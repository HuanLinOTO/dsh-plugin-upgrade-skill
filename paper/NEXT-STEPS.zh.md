## 1. 论文现在回答什么

核心问题：**迁移 skill 注入的收益如何随模型能力与推理预算变化？**

- 主分析：任务级配对的 skill-vs-noskill 比较，5 个模型点 + 1 个敏感性组（GLM 两组为 S1–S22 静态诊断题三轮中位；qwen 组为 56 题 × 3 次 scored-reward 均值 ×100；deepseek 组 23 题 × 3 次中位（terminus-2 + 旧关键词 grader）；terra/luna 为 single-shot）。统计协议：mulberry32 seed 20260907、10000 次任务级配对 bootstrap、双侧 Wilcoxon（zeros 排除并报告 nZero）。脚本与 golden 测试在 `benchmark/scripts/measure-paired-effect.mjs`。
- 后续问题（同源对照）：在同源参考资料包含相同关键事实的前提下，额外提供迁移流程指导能否提高正确性——由下表四条件设计回答，**已注册、未执行**。

| 条件 | 模型可见材料 |
| --- | --- |
| A | 无迁移资料，仅中性入口 |
| B | 通用迁移流程 |
| C | 同源参考卡片、文档与共享事实补充 |
| D | document-only 迁移流程指导 + 与 C 相同的参考资料和事实补充 |

- 该设计的主对比：同一模型、同一预算下的 **D−C**；D−A、B−A 为辅助。
- C 已经包含部分迁移指导；D 是适配后的纯文档入口。因此不能写成“未经加工的官方原文 vs 原版完整 skill”，也不能把差异直接解释为纯推理能力提升。
- 范围：DSH 单生态、回顾性、open-book 效用研究。独立事件泛化、抗误导机制、跨生态不作为这一轮必须完成的主实验。
- 可执行任务以行为验收为主；静态诊断质量、引用合规、源码约束、用量与终止状态分别报告。不能仅按 S/H 题号前缀判定任务类型。
- 两个便宜模型是当前计划；先跑通一个。具体模型、最终任务数 N、重复次数 R 和费用上限尚未冻结。

## 3. 接下来按什么顺序做

**2026-09-15 起，以下 P0 各项（四条件 16 格预演与正式跑）整体降级为 future work（FW）；主线结果已由配对实证给出。** Docker/模型链路的阻塞记录原样保留，是执行该 future work 的前置条件。

### FW-1（原 P0-1）：恢复执行环境，接通真实模型

- [ ] 检查 Docker daemon、socket 权限、可用镜像和 CLI；先跑容器探针，定位并解决具体故障。
- [ ] 检查指定模型 `gpt-5.3-codex-spark` 与 `high` 配置是否能实际调用，保存请求与可获得的服务端模型标识。身份不能验证时如实标记，不把聊天助手身份当作实验配置。
- [ ] 若指定模型不可用，记录错误，确定替代配置后再跑；禁止静默切换模型后仍标成 Spark。
- [ ] 实现或接入四条件 solver runner。已有 `pilot-study-v1.py` 只准备目录和探针；`benchmark/report-judge/codex-judge.mjs` 是裁判传输，可参考其日志设计，但不是四条件 solver。
- [ ] 宿主处理模型传输，任务环境限制执行权限；每格只挂载自己的材料，禁用 native skills、宿主配置和其他组可见性，隔离答案、测试与裁判。
- [ ] H25 在构建阶段按固定 lockfile 安装依赖，记录 Node/npm/镜像版本；保留原始 fixture。

**交付物：** 可重复运行的命令或脚本、环境配置、权限探针报告、一次真实调用的脱敏日志。先证明启动与交付成功，暂不估计 skill 效果。

### FW-2（原 P0-2）：跑完一个模型的 16 格开发预演

- [ ] 固定 H4/H6/H12/H25，不按新成绩换题；每题 A/B/C/D 各一次，独立新会话。
- [ ] 在运行前记录每格的模型、reasoning、上下文/输出限制、时间上限、工具权限、重试规则和批次花费上限。
- [ ] 平衡或随机化条件顺序，保存顺序/种子；四组采用相同预算政策。
- [ ] 验证材料可读、隔离有效、指定位置交付成功、H25 能运行行为检查；记录实际读取量、token、耗时、费用与异常。
- [ ] 先做一次单格链路冒烟检查，再完成完整 16 格；工程调试尝试另记，不挑最好一次充当正式 trial。
- [ ] 根据预演用量核价，再决定第二模型与正式规模。

**验收：** 每格都有原始报告或补丁，以及明确的运行状态；错误、超时、缺失和费用未知均显式记录。16 格属于开发证据，不是正式主表，也不足以宣称 D 优于 C。

### FW-3（原 P0-3）：补齐评分与逐题审核

- [ ] 在最终裁判配置上跑预定校准集：正确答案、正确改写、关键词堆砌、错误最终建议、否定错误建议、注入与 prompt echo；事先确定样本和重复次数。
- [ ] 优先核验 H6 的间接语义表达和 H12 的错误判别半分边界，再补其他候选任务的 QC。通过单元测试不能替代这一项。
- [ ] 把 H25 的行为通过、helper 形状、源码/依赖约束分开落实到评分输出与聚合；保留 fixture/宿主完整性门禁，不靠删除约束获得“通过”。
- [ ] 对每题记录来源、模式、可解性、允许修改范围、交付物、评分版本、材料覆盖、开发暴露和已知问题。
- [ ] 对原子事实核对保留来源和判断依据；101 个入口单元首轮分类不能标成 101 个事实全部验收。
- [ ] 记录实际提交者与维护者审核证据、日期、覆盖范围；社区 review 可证明的范围与模型答案评分有效性分开。
- [ ] 若无法安排独立人工盲评，保留 AI 辅助和维护者复核的局限。可补真实答案抽查，但不虚构双人独立标注、专家覆盖或一致性。

**交付物：** 逐题 QC 表、最终评分协议、校准细项与失败案例。准入按预先规定的质量标准决定，排除理由保留；不得按 D−C 成绩挑题。

### FW-4（原 P0-4）：冻结协议，再启动正式实验

- [ ] 固定最终 N、任务/fixture/提示/材料哈希、两模型配置、scaffold、评分器、工具与网络权限。
- [ ] 固定 R、预算与超时政策、基础设施重试政策、随机顺序、主次指标、缺失处理和统计方案。
- [ ] 审核事件分组。重复运行不是独立任务；有可靠分组时按事件族处理相关性，没有独立认证时披露来源并做敏感性分析。
- [ ] 关闭实际阻塞后实现正式冻结与校验机制。目前 `prepare-study-v1.py --freeze-check` 会直接报未就绪；不能只改 `formalRunAllowed` 或删阻塞文本宣称验收。
- [ ] 保存独立的冻结 manifest 和材料归档；冻结后的实质变更另升协议版本，并明确受影响 trial 如何处理。

**正式规模：** 两模型 × 四组 × N 题 × R 次 = `8NR`。若 N=56、R=3，则为 1,344 次 solver trial，仅是候选方案；另计开发调用、judge、校准、失败重试和存储计算成本。先按预演测得用量与价格核算，不能把 token 总量直接当美元。

### FW-5（原 P1）：聚合结果、归档与完成论文

- [ ] 每个模型分别报告 D−C，按任务先汇总重复再做配对分析；区分静态与可执行任务，给出分母、区间及相关性限制。
- [ ] 记录截止预算时的产物正确性与终止状态；timeout 不自动等于功能失败，judge_error 不记成模型零分。
- [ ] 费用含失败尝试，solver/judge 分列；分别记录输入、缓存、输出、时长；计量缺失标未知。
- [ ] 分析真实失败案例和收益集中度，保留负结果；不为了显著性只给某组追加重复。
- [ ] 归档脱敏日志、补丁、评分 packet、细项结果、哈希、依赖环境与聚合脚本；凭据不得入库。
- [ ] 用统一聚合脚本生成主表、效果区间图和成本表；据结果更新摘要、贡献、结论和限制。
