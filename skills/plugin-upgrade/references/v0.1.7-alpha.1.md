### DSH-0.1.7-A1-01 · Client UI primitives icon set renamed: every `*16` export is gone

- **Type**: breaking
- **Applies to**: client plugins rendering primitives icons (Web surface)
- **Touchpoints**: none (the host `dsh-client-ui-primitives` static module's export surface)
- **Action level**: required-if-hit
- **Symptoms**: a slot contribution that destructures any `Icon...16` named export gets `undefined` and crashes on render with React error #130 (element type invalid); the framework's slot-level error boundary unmounts the WHOLE slot entry, so the user-visible symptom is an entire surface (dock, header widget) silently vanishing with one minified console error and no request failures. First-hand fleet evidence (2026-09-22, `dsh-ui-progress` on Windows/Edge): the resident input-dock progress strip disappeared after the host upgrade; the crash surfaced in `conversation.input.dock` and the four destructured `*16` icons were the only breakage.
- **Migration recipe**: enumerate every named import from `@deepseek-ai/dsh-client-ui-primitives` in the plugin source; for each `...16` icon, look up the replacement in the target tag's primitives export surface (the 0.1.7 set observed: `IconDatabaseOutline16` -> `IconDatabaseOutlineMedium`/`IconDatabaseOutlineRegular`, `IconLoadingOutline16` -> `IconLoadingOutlineMedium`/`...Regular`, `IconWarningOutline16` -> `IconWarningOutlineMedium`/`...Regular`, `IconSparkle16` -> `IconSparkleMedium`/`...Regular`; re-check the target tag - the variant split may widen). Plugins that must run on both pre- and post-rename hosts resolve the component at runtime through a fallback chain (`*16` -> `*Medium` -> `*Regular`) instead of static named imports, and extend their unit-test module mocks with every fallback name (strict module mocks throw on undefined-export access, which masks the real failure).
- **Verification**: in a driven browser against the upgraded host, assert all three: the surface's DOM marker is present, zero `slot entry crashed` console records, and the expected network requests fire. A single "CSS loaded, no errors" check has false negatives.
- **Source**: [dsh-v0.1.7-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1); primitives export surface at tag `dsh-v0.1.7-alpha.1` (`@deepseek-ai/dsh-client-ui-primitives`); first-hand: dsh-external/dsh-ui-progress v0.10.3.
- **See also**: DSH-0.1.7-J1-26 in the version-jump companion [jump-0.1.5-rc.2-to-0.1.7-rc.1.md](jump-0.1.5-rc.2-to-0.1.7-rc.1.md) (the same rename seen from `0.1.5-rc.2`, with the full `Outline14`/`Fill14` and `ReferenceIcon`/`LinkIcon`/`PermissionIcon` mapping).

### DSH-0.1.7-A1-02 · `workspaceFiles` reads unify on `readBytes`

- **Type**: breaking
- **Applies to**: client/server plugins reading workspace file content through the `workspaceFiles` Remote namespace
- **Touchpoints**: #4 (Remote namespace calls) or direct service calls
- **Action level**: required-if-hit
- **Symptoms**: reads through the retired read methods stop working (or fail type checks at build time against the new host types).
- **Migration recipe**: the release notes state the direction only (workspace file reads unify to readBytes; plugins must migrate the old interface) - do NOT invent call signatures: open `@deepseek-ai/dsh-api-workspace-files` at tag `dsh-v0.1.7-alpha.1` (Remote types + Host service) and migrate each old read call to the `readBytes` contract (parameter shape, return envelope, chunking) from the tag's declared types. Grep the plugin for `workspaceFiles.read`, `readAll`, `readText`, `readRelated` and re-derive each against the tag.
- **Verification**: exercise one real file read through the migrated path against a 0.1.7 host and assert the bytes match the on-disk file.
- **Source**: [dsh-v0.1.7-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1); `@deepseek-ai/dsh-api-workspace-files` types at tag `dsh-v0.1.7-alpha.1`.

### DSH-0.1.7-A1-09 · Plugins can declare locale-aware title/description and a package.json icon

- **Type**: capability
- **Applies to**: plugin packaging (Plugin Manager display)
- **Touchpoints**: #7 (packaging metadata)
- **Action level**: optional
- **Symptoms**: none once declared correctly, but two `exports`-shaped failure modes are card-worthy: (1) `exports` listing only `"./locale/en.json"` while other language files sit in the directory — every language file is resolved individually as `<pkg>/locale/<lang>.json`, so `zh.json` hits `ERR_PACKAGE_PATH_NOT_EXPORTED` and `readPluginMeta` returns a metadata error diagnostic visible on the Plugins page; (2) `locale/en.json` not resolvable at all (not exported, or `files` missing `"locale/"` so npm/git installs never shipped it) — the whole localization is **silently skipped**, no error anywhere, package fields only. An empty or whitespace-only `meta.title`/`meta.description` string also surfaces as a metadata error.
- **Migration recipe**: declare display text in package-root `locale/<lang>.json` resource files. The reader is boot-stage (`readPluginMeta`, `packages/boot/app-boot/src/package-meta.ts`, contract verified at `dsh-v0.1.7-rc.1`): files are located through the Node ESM resolver **without evaluating any plugin code**, so client-only plugins get localized display too. Each file is `{ "meta": { "title": "...", "description": "..." } }`; every present field must be a non-empty string. The filename is the language id, validated `^[A-Za-z]{2,8}(-[A-Za-z0-9]{1,8})*$` and lowercased on match (`pt-BR.json` → key `pt-br`); case-equivalent duplicates are rejected (`EN.json` + `en.json` → "duplicates locale en"); every language file must resolve into the same directory as `en.json` (a subpath remap like `"./locale/zh.json": "./separate/zh.json"` errors). `locale/en.json` is the **anchor**: the locale directory is found by resolving `<pkg>/locale/en.json`, and when that fails the localization is skipped silently — so `exports` must carry the glob `"./locale/*.json": "./locale/*.json"` (a per-language entry list also works; the lone `"./locale/en.json"` entry is Symptoms (1)), and `files` must include `"locale/"` for npm/git distribution. Fallbacks when a field is absent from every dictionary: title → package.json `name` → the full module specifier; description → package.json `description` → empty string. Per-language files may carry either field alone (zh may declare only `title`), and the resulting translation map always retains `en` (`LocalizedText = string | { en: string; [locale: string]: string }`, `packages/util/package-manifest/src/types.ts`). The client resolves it through `LocaleRuntime.resolveText` (`packages/client/locale/src/client/index.ts`): a plain string stays verbatim; a map walks the active language's declared fallback chain from most specific to `en` (a `zh-CN` preference tries `zh-cn`, then `zh`, then `en`), taking the first key present. Adjacent capability on the same reader: package.json `icon` — a manifest-relative SVG/PNG/JPEG/WebP of at most 256 KiB whose realpath must remain inside the manifest directory, read into a base64 data URI; any icon failure keeps the display text and attaches the error diagnostic (the plugin stays manageable). Consumption sits in the Plugins page (`packageText`/`rowText`, `packages/client/ui-plugin-manager/src/client/presentation.ts`): package-card title/description and row-detail title/description, where a meta description outranks the `plugins.row.config` summary fallback. First-hand fleet evidence (2026-09-25): nine huanlinoto plugins (`aigc-canvas`, `tools-manager`, `mineru`, `mcp-manager`, `interpreters`, `copilot`, `preface-context`, `sidebar-brand-text`, `yet-another-subagent`) all ship `locale/en.json` + `locale/zh.json` + the exports glob + `files`.
- **Verification**: switch the client language (Settings → General → Language row) and assert the Plugins-page package/row titles and descriptions follow; `packages/boot/app-boot/tests/package-meta.spec.ts` covers the exports trap, duplicate ids, the shared-directory rule, and the icon limits; `npm pack --dry-run` lists `locale/` in the tarball.
- **Source**: [dsh-v0.1.7-alpha.1 release notes](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1) · [rc.1 `packages/boot/app-boot/src/package-meta.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/boot/app-boot/src/package-meta.ts) · [rc.1 `packages/boot/app-boot/tests/package-meta.spec.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/boot/app-boot/tests/package-meta.spec.ts) · [rc.1 `packages/util/package-manifest/src/types.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/util/package-manifest/src/types.ts) · [rc.1 `packages/client/locale/src/client/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/client/locale/src/client/index.ts) · [rc.1 `packages/client/ui-plugin-manager/src/client/presentation.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.7-rc.1/packages/client/ui-plugin-manager/src/client/presentation.ts)

### DSH-0.1.7-A1-12 · `settings.plugin.item` is retired: plugin-list shared settings move to the Plugins-page config slots

- **Type**: breaking
- **Applies to**: Web Client plugins that still register a configuration card into the retired `settings.plugin.item` keyed slot (keyed by settings namespace; last declared by `ui-settings-plugins` in `dsh-v0.1.6-alpha.1`), and plugins moving their configuration onto the Plugins page (`plugins.row.config`, `plugins.bundle.config`)
- **Touchpoints**: #5 (Web Client slots)
- **Action level**: required-if-hit
- **Symptoms**: an injection into `settings.plugin.item` never matches a declaration (no declaring package exists from `dsh-v0.1.6-alpha.2`, this set's `from` tag) and an unmatched registration stays inert, so the card silently disappears with no console record. The new slot fails the same silent way on a key mismatch: `plugins.row.config` is matched by exact string, so a key that disagrees with the bundle patch's row id simply never grows the configure control. First-hand fleet evidence (2026-09-25, `dsh-interpreters` on Windows/Web): the bundle patch declared row id `dsh-interpreters` but the client registered key `@huanlin/dsh-plugin-interpreters#interpreters` (row id written without its `dsh-` prefix) — the row-configuration control never appeared and nothing logged. A card that does move lands two further silent failures: keeping the old shared-tab card-level disclosure opens collapsed on the row's dedicated detail page — the configuration page renders nearly blank until the user clicks the fold open again (first-hand fleet evidence 2026-09-25: `dsh-plugin-preface-context`, `dsh-plugin-sidebar-brand-text`, `dsh-plugin-copilot` and `dsh-interpreters` all met this and reworked to drop the fold); and gating the contribution with `ctx.configForms.whileServed([entry], ...)` for an entry with NO volatile Config fields permanently withdraws it — settings `describe()` filters such entries out (`volatileForm(schema) === undefined`), the gate never holds, and the configure entry silently disappears with the same symptom as a key mismatch, different cause (first-hand fleet evidence 2026-09-25: `dsh-mcp-manager`).
- **Migration recipe**: boundary note first — the retirement itself landed on the preceding edge `dsh-v0.1.6-alpha.1 → dsh-v0.1.6-alpha.2` (corridor order 15; read `v0.1.6-alpha.2.md` first when it is present), where the Plugins-page package `ui-settings-plugin-manager` was renamed `ui-plugin-manager` and took over configuration hosting; this set's `from` tag is already past the retirement, and this card carries the full migration so a jump across the window is covered. This edge completed the surface (detail slots, `plugins.bundle.activation`, the `form` data channel). Ledger: settings-namespace card (`ctx.slots.inject('settings.plugin.item', ...)` keyed by namespace) → per-row page `plugins.row.config` keyed `<package name>#<row id>`, where the row id is the bundle patch insert row's `id` passed through verbatim by the Host (`rows.push({ rowId: row.id, ... })` in `packages/boot/plugin-manager/src/index.ts`) and the page matches the exact string `rowConfigKey(pkg.name, row.rowId)` — take the id from your own `cordis.patch.yml`, never from the module name or a shortened package suffix; derive the key once in a zero-dependency leaf module (``const ROW_KEY = `${PACKAGE_NAME}#${ENTRY_ID}` `` — single source of truth, no scattered literals) and pin it with a key contract test asserting ENTRY_ID === the `cordis.patch.yml` insert-row id, PACKAGE_NAME === the `package.json` name === the patch row `name`, and ROW_KEY === their concatenation — a drifted key then fails CI instead of silently hiding the control (first-hand fleet evidence 2026-09-25: after the `dsh-interpreters` miss above, `dsh-plugin-tools-manager` row-config-key.spec ×4, `dsh-plugin-aigc-canvas` entry-identity.spec ×3 and `dsh-mcp-manager` row-key.spec ×3 all added this guard). Bundle-level form → `plugins.bundle.config` keyed by package name (renders `view: 'page'` only); official-plugin cards → `plugins.item` (OCCUPIED by the official settings pages — a bundle's configuration belongs in the two config slots; the slot is a plain list with NO registration gate, so a third-party card registered there renders inside the Official group and reads as an official plugin — first-hand fleet evidence 2026-09-25: `ds-harness-remote` v0.4.x registers `plugins.item` beside its correct `plugins.bundle.config` and its card lands in the Official group; third-party plugins use the two config slots only); detail-page contributions → `plugins.detail.actions`/`.badge`/`.section` (subject-typed); post-enable guidance → `plugins.bundle.activation`. Shared-card chrome: the old `settings.plugin.item` card rendered inside a SHARED tab where multiple plugin cards stacked, so each card carried its own card-level disclosure — header open/close button, chevron, `aria-expanded`, default collapsed; on `plugins.row.config` the card renders on the row's DEDICATED detail page, which draws its own title/icon/breadcrumb and where the card is the page's only content, so the card-level fold becomes redundant nested chrome and its default-collapsed state shows a near-blank configuration page that costs an extra click. Delete the disclosure with the migration — the open/close state, the header toggle button, the chevron, `aria-expanded`, and the expand/collapse locale keys with their 19-language coverage dictionary — keep the content permanently expanded, and keep always-visible whatever degraded/unavailable notice was always visible. Boundary: entry-level folds INSIDE the content (provider entries, tool prefix trees, profile rows, server entries) are list organization, not card chrome — keep them; the discriminator is whether the toggle folds the WHOLE card (delete) or a single entry of a list inside the card (keep). First-hand fleet evidence (2026-09-25): `dsh-plugin-preface-context` (preface-card.tsx `aria-expanded` header), `dsh-plugin-sidebar-brand-text` (BrandTextCard, a self-described expandable card with controller-held open state), `dsh-plugin-copilot` (chevron + `expanded = open || unsupported || loginRevealed` forced-expand patch) and `dsh-interpreters` (`userOpen` default collapsed) — all four reworked to drop the fold. Data channel: `PluginConfigViewProps { view: 'summary' | 'page', form?: ConfigPageForm }` with `ConfigPageForm = { state: ConfigFormSnapshot<Record<string, unknown>>, mutate }`; the page assembles `form` only when settings `describe()` serves the entry's namespace, and `describe()` drops entries whose fiber is not `ACTIVE`, so a stopped row hands the entry `form: undefined` — render a fallback instead of assuming the form. Gating: register the contribution inside `ctx.configForms.whileServed([<entry id>], () => ctx.slots.inject('plugins.row.config', ...))` so the whole contribution is withdrawn while the Host serves none of the namespaces (fleet practice: `dsh-plugin-preface-context`; without it a deployment that never composes the owning row keeps a dead entry). Gating exception: the gate condition is settings `describe()` serving the entry's form, and `describe()` drops entries whose schema declares no volatile fields (`volatileForm(schema) === undefined`), so a whileServed around an entry with zero volatile Config never holds and the contribution is permanently withdrawn — the row-config entry silently disappears. A row-config card that manages OTHER rows' data (registry-manager shape, no volatile Config of its own — fleet practice 2026-09-25: `dsh-mcp-manager`, whose panel manages the official `@deepseek-ai/dsh-mcp-client` insert rows) therefore registers with a bare `ctx.slots.inject('plugins.row.config', ...)` (waiting on the slot declaration only), never reads `props.form` (permanently undefined for it) and carries its data over its own channel; whileServed stays for editor-type plugins whose own entry declares volatile Config (the preface-context shape). Peer: `@deepseek-ai/dsh-client-ui-plugin-manager` is a type-only peer — merge the contract by `import type` (module augmentation) and register through `ctx.slots`; the contract forbids importing the package at runtime.
- **Verification**: on the upgraded host, with the owning row enabled, the row shows its configure control and an edit round-trips through `form.mutate` (the value lands under the entry's `config` in the profile patch); disable the row and assert the control disappears and the page renders its no-form fallback; grep the plugin for `settings.plugin.item` injections (must be empty) and assert every `plugins.row.config` key string-equals `<npm package name>#<patch row id>` (the key contract test above keeps this true in CI); then open the row's configuration page cold — every field must be visible immediately, with no card-level collapse/expand toggle and no second click to see settings (entry-level folds inside the content may remain).
