# Troubleshooting · post-migration symptom lookup

> Quick-reference table for tracing symptoms back to root causes and their cards, for debugging after Mode C migrations. It is not a decision flow, nor a complete fault catalog: root-cause confirmation still rests on the card recipes and the target tag's source; symptoms not listed here return to the pre-flight touchpoints and the layered validation checklist for layer-by-layer triage.

| Symptom | Most likely root cause | Card to check first |
|---|---|---|
| Panel/floating ball silently disappears, the plugin is absent from the boot graph, usually with no error at all | `dsh.client.inject` still references a removed package (phantom dependency), so the row never enters the graph; or the registration id / assembly row name does not match the package name; or the plugin is `disabled: true` at the patch layer | [DSH-0.1.2-A1-25](v0.1.2-alpha.1.md), [DSH-0.1.2-A1-26](v0.1.2-alpha.1.md) |
| Startup assertion `loaded without registering "<id>"` | the client bundle's registration id (`__ModuleLoader__.load` id / tsdown banner `PLUGIN_ID`) ≠ package.json `name`, or the assembly row's `name` is not the bare package name | [DSH-0.1.2-A1-26](v0.1.2-alpha.1.md) |
| `web boot: N entries did not activate`, `waiting for service: apiProxy` | 0.1.2 removed the ApiProxy transport layer, so a row with `require: ['apiProxy']` stays pending forever; or inject still references a removed package | [DSH-0.1.2-A1-01](v0.1.2-alpha.1.md), [DSH-0.1.2-A1-25](v0.1.2-alpha.1.md) |
| Plugin loads but features half fail, console reports a factory error | the session-content read path is broken (per-session `.nodes` snapshot removed) or the composer DOM has drifted | [DSH-0.1.2-A1-27](v0.1.2-alpha.1.md), [DSH-0.1.2-A1-28](v0.1.2-alpha.1.md) |
| `workspaces.connectWorkspace is not a function`, or workspace connect/pick throws while the plugin still boots | `ctx.workspaces` survived the Client Runtime split as list/CRUD only; navigation and the directory picker moved to `ctx.uiWorkspace`. `baselinesReady` / `recentWorkspaceId` are gone | [DSH-0.1.2-A1-32](v0.1.2-alpha.1.md), [DSH-0.1.2-A1-25](v0.1.2-alpha.1.md) |
| Old host reports `missed the module table` | the client bundle hard-requires a module unique to the target cohort during evaluation (cross-cohort coexistence problem) | rollup [R-02](rollup-0.1.2.md) |
| Browser: `Failed to load plugins: failed to import loader entry <id>`, then **zero** plugins register | the named `<id>` is only the first awaited entry (e.g. `dsh-typert-registry`, innocent); some plugin's client bundle contains raw ESM (a top-level `import`), and one ESM token fails the WHOLE classic-`<script>` bundle combo at compile time. Client halves register through `window.__ModuleLoader__.load({ id, factory })` with `require("react")` inside the factory — never bare ESM. Bisect the patch layer's `insert` rows to find the culprit | the `plugin-runtime-debug` skill's symptom families |
| `slot "<name>" is not declared (a parent entry's children table must declare it)` at apply time | the plugin registers a slot that another entry owns/declares (`settings.section`, `conversation.*`…) with a bare `ctx.slots.register` — apply order is undefined, so the registration can land before the owner's declaration. Wrap it: `ctx.slots.inject(name, () => ctx.slots.register(...))`; the registrant passes only `name`/`id`/`order`(`label`), never `kind`/`scope` | [DSH-0.1.2-A1-25](v0.1.2-alpha.1.md), [DSH-0.1.2-A1-26](v0.1.2-alpha.1.md) |
| 刚发布的版本，插件自己的更新徽章就显示「新版本 vX.Y.Z 可用」且指向刚发布的那个 tag | 客户端 bundle 里的版本常量是**构建时**从 package.json 内联的：构建先跑、版本号后 bump，发布的 bundle 还带着旧常量，自更新检查拿它对比镜像最新 tag 必然报「有更新」。镜像/tag 完整性无关。修复顺序：先 bump → 再 build → 提交/打 tag 前在产物里 grep 新版本常量确认 | benchmark 任务 S19-phantom-update-stale-host（plugin-upgrade 基准库）· plugin-release publish-playbook |
| 客户端 UI 已出现新功能，但新增的宿主路由对新扩展名返回 404（同路由旧类型 200），且磁盘上的宿主半产物已包含新白名单 | 更新平面不对称：client bundle 每次刷新重新拉取（no-cache），而宿主半在 apply 时一次性注册路由（闭包持有旧白名单），运行中的进程要等**宿主重启**才换新。归因探针：旧类型 200 + 新类型 404 + 磁盘产物含新白名单 ⇒ 运行进程早于改动。「插件热更新」只覆盖 client 面 | benchmark 任务 S19-phantom-update-stale-host（plugin-upgrade 基准库）· plugin-runtime-debug |
| 渲染基于会话 payload 的文件出现裂图，但源文件本身完好（XML/语法校验通过），重读后 payload 又是干净的 | 会话日志里的 read 结果文本可能被上游组装环节损坏（真实案例：源 232 行被 247 行尾部在公共前缀 "stro" 处错位拼接，中间 15 行丢失）。插件必须把会话 payload 当**不可信渲染输入**：先 DOMParser/语法校验再渲染；优先走宿主 asset 路由读磁盘原始字节；损坏要上报上游，而不是在插件里「修文件」 | benchmark 任务 S19-phantom-update-stale-host（plugin-upgrade 基准库）· plugin-runtime-debug |
| 重启后宿主启动即崩：`duplicate loader entry id: <id>`（`dsh-app-boot` → `cordis-plugin-loader` → `EntryGroup.update`） | 在 profile 的 `cordis.patch.yml` 里手动 `insert` 了一个 bundle 层已提供的插件 id——Cordis 把重复 insert 视为致命错误（非静默覆盖）。0.1.5 系列新增的 `workspace-files` / `ui-sidebar-*` 等已由 web-app bundle 自动提供，升级 profile 无需手动补插。删除 profile patch 中重复的 insert 块即可恢复启动；如插件确实不可用，根因是 compose/artifact 缺口而非缺少 insert（见 discussion [#5999](https://github.com/deepseek-ai/deepseek-harness/discussions/5999)） | Cordis 组合规则（无对应版本卡，跨版本通用） |
| Windows 上原地升级/替换全局 dsh 或插件文件报 `EBUSY` /「正由另一进程使用」，关掉浏览器标签也不释放 | 运行中的 dsh web 宿主进程持有已加载的宿主半/原生模块文件句柄（真实案例：`koffi.node` 被宿主 PID 锁定）；文件锁在宿主不在浏览器。顺序：完全停止宿主进程 → 再执行文件替换/升级；升级把宿主搞坏时按 dist-tag 钉精确版本回退（`npm i -g @deepseek-ai/dsh@<已验证版本>`，`latest` tag 可能滞后），恢复后再排查新版本问题 | benchmark 任务 S12-global-upgrade-ebusy-trap（plugin-upgrade 基准库）· precision-checklist 钉版本规则 |
| link/junction 安装的插件：往 profile 的 `node_modules` 里 `Copy-Item` 报 EBUSY，rename-aside 绕锁后**源目录和 profile 同时**只剩 `.old2` 文件 | profile 条目是 Junction（`Get-Item` 的 `LinkType`/`Target` 可证），repo 树与安装目录是同一物理位置：repo 编辑本就即时生效，复制从来都是多余动作；rename 穿过 junction 重命名的是唯一源文件。恢复：`.old2` 改回原名 → `node --check` 验证 → 完全停宿主 → 重启 `dsh web` → 浏览器硬刷新。动手前先查 `LinkType`/`Target` 判断安装模式；「复制进 node_modules」对 link 安装是有害建议 | benchmark 任务 S14-link-install-lock-trap（plugin-upgrade 基准库）· v0.1.3-alpha.1 卡 junction 语义 |
| Windows 上 `pnpm install` 失败：`gyp ERR! find VS` / `fs-ext` 原生构建失败，机器没有也不会装 Visual Studio | `fs-ext` 被 session-persistence **静态 import**，`--ignore-scripts` 跳过构建也过不了模块加载；而 Windows 运行时走命名内核信号量（`acquireLockHandleWin32`），`flock` 是 POSIX 分支死代码。修法走仓库现有 pnpm patch 先例：win32 跳过 node-gyp + 纯 JS fallback，非 Windows 保留原生；不要为此装 Visual Studio，不要改上游依赖 | [DSH-0.1.3-A1-03](v0.1.3-alpha.1.md) · benchmark 任务 S20-msvc-flock-trap（plugin-upgrade 基准库） |

- **Source**: real migration of dsh-input-history 0.1.1 → 0.2.0 (2026-08); rows cite their sources individually — the session-payload corruption row comes from [discussion #5120](https://github.com/deepseek-ai/deepseek-harness/discussions/5120), the duplicate loader entry row from [discussion #5999](https://github.com/deepseek-ai/deepseek-harness/discussions/5999). The EBUSY / junction / fs-ext rows come from the corresponding real migration sessions (2026-09), preserved as benchmark tasks S12/S14/S20.
